New issues found in sweep 2

A. FIXED — the deferred online job journal is preserved while parked.
   SaveManager.save() calls writeJobJournal(serialize().farmJobs), and writeJobJournal
   removes the key whenever the queue is empty (SaveManager.ts:104-108). Because the
   replay is now deferred, the queue IS empty at boot, and main.ts:1125 calls
   saveManager.save() immediately after load() — before the writer is available. The
   journal key is deleted on every start. Verified with a throwaway probe test against
   the real SaveManager: after that save(), localStorage[<account>::farm-jobs] is null.
   In the happy path pendingOnlineJobs still holds the intents in memory, so the replay
   works and rewrites the journal; but any reload/crash before the writer arrives loses
   them for good. Fix: keep the journal intact while pendingOnlineJobs is set (write the
   parked value through instead of clearing), or defer the first checkpoint until after
   restoreOnlineJobs(). SaveManager now writes the parked journal through pre-writer
   checkpoints, and only clears the parked copy after restorePending succeeds.

B. FIXED — online job replay now follows every transition to writer ownership.
   onWriterAvailable is fired only from EconomyClient.start() when bootstrap.writer
   .status === "mine" (economy.ts:161), and main.ts:1402 is its only listener.
   recover(), reloadAfterConflict(), reconnectAfterFailure(), and takeOver() all reach a
   writable channel without firing it. So:
    * first bootstrap fails (network blip), recovery succeeds seconds later -> intents
      stranded in memory forever, journal already erased by A;
    * another device holds the writer -> writer-lock UI; "Take over" reloads the page,
      and after the reload the journal is gone (A), so the queued actions are lost.
   Combined with A this means the reported defect still reproduces whenever the first
   bootstrap does not immediately hand this tab the writer. Fix: drive the replay off
   setOnlineWritable(true) (or call restoreOnlineJobs from every path that reaches a
   live writer) — it is already idempotent and safe to call repeatedly. The centralized
   ownership-sync path now fires onWriterOwned for initial boot and recovery bootstraps;
   main uses that signal to enable writes and replay the parked journal.

C. REVIEWED — writer polling retained; unrelated fruit-tree balance overrides reverted.
   Nothing in this document asks for either change, and both alter live behaviour:
    * Writer-lease polling redesign. The fixed 45 s ownership poll became an adaptive
      3-minute timer rescheduled by every successful writer-protected response; the
      server heartbeat throttle went 60 s -> 5 min; accounts.last_online_at moved off the
      session touch (db.ts sessionAccount) onto writer.validate/beginOperation with a
      5-minute throttle. I checked the timing: worst-case lease staleness is 6 min
      against WRITER_IDLE_MS of 10 min (4 min margin), and the client's
      writerProtectedRequest list matches the server's writerProtectedMutation exactly,
      so the mechanism is sound. Two behaviour changes to accept knowingly: a displaced
      idle session now discovers its takeover in <=3 min instead of <=45 s, and
      last_online_at no longer advances for a signed-in tab that never takes the writer.
    * Fruit-tree balance (reverted): Olive Tree level 1 -> 5 (placeables.json, prep_placeables.py,
      server/src/objectCatalog.ts), Lemon harvestValue 15 -> 35, Orange 15 -> 18. No
      client/server desync — server/src/v3/engine.ts imports placeables.json directly —
      but this is an economy change, not a defect fix.

D. FIXED — the redundant HUD-owned crop-hover ticker was removed. main.ts remains
   the sole owner of the 250 ms hover refresh and clearing rules. Previously hud.ts started
   window.setInterval(() => this.renderCropHover(), 250) in the constructor (never
   cleared), while main.ts re-pushes the hover every 0.25 s and owns the clearing rules.
   Harmless, but the hud interval is now dead weight and re-shows the card from state
   main.ts is responsible for clearing.

E. FIXED — bootstrap timers are translated before the first frame. SaveManager
   .fromBootstrap() places fruit trees with the raw server readyAt, and only the later
   economy onObjectState pass (main.ts:1274) re-syncs the translated value. The
   offline cached-snapshot path never gets the translated value at all, so a skewed
   clock shows a wrong tree countdown in offline view — the same class of bug the
   Insta-Grow fix eliminated for crops. Crop plantedAt, object readyAt, and raid lastRaidAt
   now share one clock helper and one captured client timestamp during hydration.


New issues found in sweep 3

F. FIXED — a parked journal refused by a busy JobSystem is now retried, not discarded.
   JobSystem.restorePending() early-returned on `if (this.busy) return;` without
   signalling that it had done nothing, and restoreOnlineJobs() cleared
   pendingOnlineJobs regardless, then overwrote the journal with the live queue. Proved
   with a probe. The sweep-2 throw-retry guard did not cover it — the bail is silent,
   not an exception — and it was reachable because enqueueTool (main.ts:1625) has no
   onlineGameplayBlocked() guard, so any plow/plant tap between load() and onWriterOwned
   makes the queue busy: one bootstrap round-trip normally, but 2-60 s on the recovery
   backoff path, where the farm stays interactive behind the "Online gameplay paused"
   toast. restorePending now returns whether it took responsibility for the save (an
   unusable save is consumed; a busy refusal is not), SaveManager keeps the journal
   parked on a refusal, and checkpointJobs — already fired on every queue change —
   re-offers it as soon as the live job finishes. A `draining` flag guards the re-entry
   from restorePending's own enqueues. Covered by both a real-JobSystem contract test
   and a SaveManager refuse-then-retry test.

G. FIXED — Epic Boss timers now share the one clock helper.
   The run projection was the last authoritative epoch crossing untranslated:
   SaveManager.fromBootstrap passed boot.gameplay.epicBoss straight through, and economy
   pushed the raw projection from adoptGameplay / adoptEpicBossResult /
   adoptEpicBossActivation. Its expiresAt / encounterStartedAt / retryReadyAt were then
   compared against the local clock in EpicBossManager.ts:31, :35, :46, :52, :64 and in
   the "days remaining" pill at main.ts:1992, so a skewed client could read an active
   event as expired (or the reverse). src/net/clock.ts gains epicBossRunToClient(),
   which moves all five epochs at once — no caller can translate some and forget the
   rest — and leaves the 0 sentinel alone so "not started"/"not completed" cannot drift
   into a real time. /epic-boss/activate, /end and /start now return serverTime as the
   anchor (finish already did); a missing anchor degrades to a zero offset, so the
   client stays correct against an older Worker. Covered by src/net/clock.test.ts.

  variant's tint, which needs neutral base art — every other family is authored
  greyscale. flowerbed.png is not: its petals are magenta and its TileProperties row

QUEST RAIL UNDER-REPORTED IN ONLINE MODE (field report: "I put in two giant lollipops
and it shows in task that I still need to buy one more", quest 27 Candyland).

  FIXED in src/quest/QuestSystem.applyAuthoritativeChanges. views() draws the
  OPTIMISTIC preview in preference to the confirmed server counts, and nothing ever
  cleared that preview (only restore() did). The preview grows solely from events this
  client posts locally, so any progress the server counted without a matching local
  post — another device, or a command whose optimistic post was skipped — sat below
  the truth and kept SHADOWING it for the rest of the session. Confirmed counts now
  merge in with max(), and the preview is dropped once the server has caught up, so
  the rail still shows an unconfirmed local event but can never display less than the
  server has already granted. Two regression tests in QuestSystem.test.ts.

  The server side was verified correct first: applyCommandBatch counts two lollipop
  buys as 2 whether they arrive in one batch or two.

  NOT RULED OUT as the cause of this particular report: 11 of the 25 buy-objectives
  name an item the market sells BEFORE the quest exists, so a purchase made early
  earns no credit. Quest 27 wants Giant Lollipops (sold at 21) and Balloons (21) at
  quest level 23, and Cotton Candy Trees (sold at 7) at 23 — a 16-level gap.
  Distinguishing test for a reporter: RELOAD. The preview bug clears on reload (the
  count jumps to the right value); an early purchase does not.


EPIC-BOSS PRIZES WERE UNCLAIMABLE (field report: "you can put them into ur farm, the
system calls it a bad item and rolls it back", Dr. Groundhog).

  FIXED, and it was NOT limited to Dr. Groundhog: not one of the 50 decor prizes
  across all 8 epic bosses had an entry in public/assets/raids/drops.json. Claiming a
  Received item runs storage.claim -> planClaim -> dropEcon(name), which reads that
  table, so every epic prize resolved to "bad_item" and the optimistic placement was
  rolled back by the next reconcile. planStore and planRetrieve read the same table,
  so a prize could not be shelved either — the report understated the blast radius.

  The prize names/tiles were already in each boss's catalog.json; prep_drops.py now
  emits them alongside the raid drops (icon "", since the prize's art is the placeable
  its `tile` names), and server/src/raidLootCatalog.ts mirrors the 50 new rows.
  Guarded by server/test/storage.test.ts (every prize claims, stores and retrieves)
  and server/test/loot.test.ts (every prize resolves; none leaked into a raid tier).

  Two knock-on improvements: the Received card now resolves each prize's real art
  (drgroundhogLabTable.png etc.) instead of falling through to nothing, and
  ownedLootCounter can resolve a prize by name without the caller passing its tile —
  the loot.test.ts case asserting the opposite was encoding this very gap.

  A SECOND gate sat behind the claim: object.refund resolves through objectEcon, and
  40 of the 50 prizes had no row in server/src/objectCatalog.ts either — so a prize
  that now claimed fine still could not be SOLD ("bad_item"). Every category-"reward"
  placeable is mirrored now, and objectCatalogSync.test.ts gained the coverage check
  that was missing all along (its price/level tests skip absent keys, so a GAP was
  silent; only orphans in the other direction were caught).

  Their price came with a trap. The source sold Epic prizes for brains, to let you
  skip the fight, so their placeables rows carried 1-4 brains and refunds convert at
  1,000 gold each. Reforged never sells them (category "reward" is absent from the
  Market), so honouring that price meant a free prize cashed out for 1,000-4,000
  gold. They are priced at cost 0 now, exactly like the other 54 earned decorations,
  which pays the game's one-gold minimum. prep_placeables.py treats the Epic tiles as
  reward-only so a regenerate keeps it that way.

  NOT REPRODUCED: the second half of the report, that a prize does not appear on the
  victory loot screen. openRaidResult renders an epic prize correctly when given one
  (verified live), every boss's lootIcon file exists, and both the offline and online
  paths pass the prize into the view. The roll is 35% per cleared level, so a run that
  granted nothing is the likeliest reading. Worth re-asking the reporter once the
  claim fix is deployed.
